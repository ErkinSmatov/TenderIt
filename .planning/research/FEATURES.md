## Research Answers

### 1. Existing Kazakhstan Tender Aggregator Feature Sets

**Known competitors and their positioning (MEDIUM confidence — from training data, not live scrape):**

**zakup.smart.kz** — Positioned as a "smart search" layer over goszakup. Key features:
- Keyword + КТРУ filter search over goszakup data
- Email notifications for saved search profiles
- Company profile with BIN lookup (egov integration)
- Tender bookmark / watchlist
- Export to Excel
- Paid subscription tiers (basic = 3 saved searches, pro = unlimited)

**tenderbot.kz** — Telegram-bot-first product:
- Bot sends new tenders matching keyword/КТРУ filters to Telegram
- Web dashboard is thin; bot is the product
- No document handling, no submission
- Free tier (limited) + paid monthly

**tender.kz** — Directory-style aggregator:
- Broader coverage including Samruk-Kazyna, construction tenders
- Filter by region, sum, category
- Historical analytics (winner prices, participant counts)
- Paid "monitoring" plans
- No submission automation

**Common pattern across all competitors:** They stop at discovery + notification. None automate document assembly or ЭЦП signing. This is TenderIt's whitespace.

### 2. Document Types Required for Tender Submissions in Kazakhstan

**HIGH confidence — governed by Закон РК "О государственных закупках" №303-V and goszakup portal rules.**

#### For конкурс (open tender) — most common:
| Document | Notes |
|----------|-------|
| Заявка на участие | Generated by portal; requires ЭЦП signature |
| Техническое предложение | Must match техспецификации лот за лотом |
| Ценовое предложение | Price per unit × quantity |
| Справка о зарегистрированном юрлице / ИП | From egov или ЦОН — срок действия 3 месяца |
| Свидетельство о регистрации (для ИП) | Or устав for ТОО |
| Налоговая задолженность справка | Not required upfront but required at award stage |
| Лицензия / сертификат соответствия | Only for regulated goods/services (pharma, construction, etc.) |
| Квалификационные требования ответ | Free-form or templated depending on customer |

#### For запрос ценовых предложений (RFQ / ЗЦП) — simple purchases:
| Document | Notes |
|----------|-------|
| Ценовое предложение | Core document — price + delivery terms |
| Тех. предложение | Often a simple 1-page document |
| ЭЦП подпись | Required even for ЗЦП |

#### For MP.kz (commercial tenders):
- Requirements vary per buyer
- Less standardized than goszakup
- Often: company profile + price + optional certificates

**Critical insight:** For goszakup, the portal itself generates the application XML structure — the supplier fills fields + attaches PDFs + signs the package with ЭЦП. Document auto-fill means pre-populating those fields from a stored company profile, not substituting PDFs wholesale.

### 3. Most Important Tender Search Filters (Kazakhstan Context)

**HIGH confidence — based on goszakup portal structure and procurement law.**

Priority order for the target user (SMB director scanning for relevant work):

| Rank | Filter | Why Critical |
|------|--------|--------------|
| 1 | Ключевые слова / наименование тендера | First instinct of every user |
| 2 | КТРУ код | Defines goods/services classification — most precise filter |
| 3 | Дата окончания подачи | SMB directors work last-minute; "ends in 3 days" view essential |
| 4 | Сумма (min/max) | Filters out micro-lots (<50k ₸) and mega-contracts beyond capacity |
| 5 | Метод закупки | конкурс / ЗЦП / из одного источника — ЗЦП is faster/easier |
| 6 | Заказчик (регион / ОКПО) | Companies often work regionally |
| 7 | Статус | Новый / Идёт подача / Завершён |
| 8 | Отрасль / категория | Broader than КТРУ; useful for first-pass browsing |

**КТРУ (Классификатор товаров, работ и услуг)** is a hierarchical code system. Users know their 2–4 digit segment but rarely the full 10-digit code — the filter UI must support prefix search / tree navigation, not exact-code entry.

**Region filter nuance:** goszakup "region" refers to заказчик's registration region, not delivery region. Some buyers procure centrally but deliver regionally — this causes user confusion. Flag for documentation/tooltip.

### 4. Tender Lifecycle on goszakup.gov.kz

**HIGH confidence — this is defined by law and well-documented.**

```
ANNOUNCEMENT PHASE
  Заказчик публикует объявление о закупке
  → Указывает: лот(ы), КТРУ, техспецификация, НЦК (начальная цена контракта),
    требования к поставщикам, срок подачи
  → Срок подачи: minimum 10 рабочих дней for конкурс; 3–5 дней for ЗЦП

APPLICATION PHASE (supplier side)
  → Поставщик логинится через ЭЦП (NCALayer)
  → Заполняет заявку (поля + вложения)
  → Подписывает пакет ЭЦП
  → Портал фиксирует timestamp — опоздание = автоотказ

EVALUATION PHASE
  → For конкурс: Конкурсная комиссия оценивает по критериям (цена + квалификация)
  → For ЗЦП: Автоматический выбор наименьшей цены
  → Срок: до 10 рабочих дней после закрытия подачи

AWARD PHASE
  → Протокол итогов публикуется
  → Победитель получает уведомление
  → Договор подписывается ЭЦП на портале в течение 5 дней

POST-AWARD
  → Исполнение контракта: акты, накладные — тоже через портал
  → Рейтинг поставщика обновляется
```

**Key timing facts:**
- Applications must be submitted before deadline to the minute — portal hard-closes
- ЭЦП key must be valid (not expired) at moment of signing
- NCALayer must be running on the user's machine — if it's closed, signing fails silently or with cryptic error
- For конкурс, corrections after submission are not allowed

### 5. Why SMB Companies Fail to Submit Tenders

**HIGH confidence from known patterns; MEDIUM confidence on relative frequency.**

#### Category A: Timing failures (most common)
1. **Пропущен дедлайн** — User finds tender 1–2 hours before close; NCALayer setup takes longer than expected. The 3-click flow directly solves this.
2. **ЭЦП ключ истёк** — RSA key validity is 1 year for физлица, 2 years for юрлица. Users forget to renew. Portal rejects silently.
3. **NCALayer не запущен** — Desktop app isn't running; WebSocket connection fails; user gets confused error.

#### Category B: Document failures
4. **Справка с истёкшим сроком** — Government certificates have 3-month validity. User uses an old one stored on desktop.
5. **Несоответствие техпредложения** — Technical proposal doesn't address all required specifications point-by-point. Most common rejection reason at evaluation stage.
6. **Отсутствует лицензия** — User didn't read qualification requirements; licensed activity requires proof.

#### Category C: Portal UX failures
7. **Неправильный формат файла** — Portal accepts PDF only for certain fields; user uploads DOCX.
8. **Превышен размер файла** — goszakup has file size limits (~5MB per attachment). Scanned documents often exceed this.
9. **Подпись на неправильный документ** — User signed the wrong version of the document.
10. **Заявка создана в черновике, не отправлена** — Portal has a "draft" state; user thinks they submitted but didn't click final "Подать".

#### Category D: Knowledge gap failures
11. **Не понял метод закупки** — Applied to a ЗЦП thinking it was a конкурс; different rules apply.
12. **Неверный лот** — Multi-lot tender; user applied to wrong lot number.

**TenderIt design implications:**
- Document validity tracking (expiry dates) is a high-value feature
- Clear submission confirmation (not ambiguous "draft saved") is critical
- NCALayer status indicator before user starts filling form prevents wasted effort
- ЭЦП expiry warning should appear on dashboard, not just at signing time

### 6. Expected Notification Cadence

**MEDIUM confidence — inferred from target user behavior and competitor patterns.**

**What users expect:**
- Instant (or near-instant) notification when a matching tender appears — especially for ЗЦП which can close in 3–5 days
- Daily digest option for users who don't want per-tender pings
- Deadline reminders: 48h before close, 24h before close for saved/tracked tenders
- Award notification: "You won" / "You lost" once results publish

**Channel preferences in Kazakhstan SMB context:**
- Telegram is by far the dominant async communication channel — higher open rate than email
- WhatsApp is second (especially for older directors)
- Email open rates for KZ SMB are low — useful as backup, not primary
- SMS is costly and seen as spam; do not use

**Cadence anti-patterns to avoid:**
- Notifying about every tender regardless of filters = instant unsubscribe
- Notifying about tenders already past deadline (data freshness bug) = loss of trust
- No "quiet hours" setting leads to 2am Telegram pings = user mutes bot

Features competitors don't offer that create real competitive advantage.

| Feature | Value Proposition | Complexity | Notes |

| Document expiry tracking | Proactively warns user before справка expires; prevents submission failures | Medium | Store expiry date per document; cron job for warnings |

## Anti-Features

Deliberately NOT build in v1. These would consume sprint capacity without validating core value.

| Anti-Feature | Why Avoid | What to Do Instead |
|--------------|-----------|-------------------|
| Multi-company account management | Core user is a single-company director; adds auth complexity with zero MVP validation value | Hard scope boundary; revisit after 50+ paying users |
| Analytics dashboard (win rates, market prices, competitor tracking) | Interesting but not on the critical path to first submission | Defer to v2; store raw data now so analytics are possible later |
| AI-generated technical proposals | High complexity, high hallucination risk in regulated submissions; wrong техпредложение = disqualification | Do not build; flag as v3 idea |
| Mobile app (iOS/Android) | Web is sufficient for the use case; NCALayer only has desktop client anyway — mobile signing is a different flow entirely | PWA meta tags for mobile web; native app if NCALayer adds mobile support |
| Samruk-Kazyna / eGP platform integration | Different API, different auth, different document requirements; stretches v1 scope | v2 after goszakup is proven |
| Subscription / payment system | MVP is validation-first; billing adds 2–3 weeks of scope | Defer; free access during validation |
| Email-primary notification | Low open rates for KZ SMB; not worth building primary flow around | Email as fallback only, not primary channel |
| Tender "recommendation engine" (ML-based) | Requires training data TenderIt doesn't have yet; over-engineering for MVP | Saved searches + manual filters are sufficient |
| Bulk application (apply to 10 tenders at once) | Risk of incorrect submissions; NCALayer requires conscious user action per signature | One application at a time; deliberate UX |
| Supplier rating / reputation tracking | Nice to have; zero bearing on v1 core value | Track the data; surface in v2 |
| Integration with accounting systems (1C, etc.) | Not relevant until contract execution phase | Out of scope entirely for v1 |
| CRM / team features (assign tender to employee) | Target user is the sole procurement person; team features imply enterprise, not SMB | Explicit no for v1 |

## MVP Recommendation

**Prioritize (must ship for validation):**

1. Auth + Company Profile (БИН, company data)
2. Tender Search — keywords + КТРУ + sum + deadline + method + region
3. Telegram notifications for saved search profiles
4. Document Vault with expiry date metadata
5. NCALayer WebSocket integration + ЭЦП signing
6. goszakup auto-submit via official API
7. Application status tracking (Черновик → Подписано → Отправлено)
8. ЭЦП key expiry warning on dashboard (cheap, high value)
9. NCALayer connectivity status indicator (cheap, prevents support tickets)

**Defer to post-MVP (after first 10 real submissions):**

- MP.kz integration — validate goszakup first; same architecture scales
- WhatsApp notifications — Telegram is sufficient for v1
- One-click re-application — requires application history UX
- Application history + outcome log — requires results polling
- Smart КТРУ suggestion — nice UX but saved searches with manual КТРУ work for v1
- Document expiry warnings cron job — store expiry dates in MVP; automate alerts in v1.1

## Open Questions (Require Validation)

1. **goszakup official API terms:** Does the supplier-facing API allow third-party application submission, or does it require submission through the portal UI only? This is the single most critical technical assumption in the entire product. Needs official API documentation review or direct contact with goszakup support.

2. **NCALayer WebSocket protocol stability:** NCALayer has had breaking protocol changes in past versions. Need to verify current WebSocket API contract and whether it's versioned/stable.

3. **MP.kz API availability:** Does MP.kz expose an official supplier API, or is aggregation via scraping? Scraping violates ToS and is fragile.

4. **File size and format constraints on goszakup:** Exact limits need verification against current portal documentation — these change with platform updates.

5. **ЭЦП certificate types:** юрлица use RSA keys issued by НУЦ РК; физлицо-ИП may use different certificate. Need to confirm which certificate types TenderIt must support for the ИП segment of the target market.

6. **Rejection reason availability in API:** Whether goszakup API returns machine-readable rejection reasons (enabling the application outcome log differentiator) needs API documentation confirmation.
