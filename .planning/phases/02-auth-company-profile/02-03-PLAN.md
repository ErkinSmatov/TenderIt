Second wave. Completes AUTH-02 (persistent sessions) and AUTH-04 (logout).

- POST /api/auth/refresh: reads refresh_token cookie, decodes (validates exp + type=="refresh"),
  reads stored value from Redis (refresh_token:{user_id}), verifies they match, rotates

Purpose: Token rotation closes the replay-attack hole (Pitfall 6). Logout closes
the user-visible session termination requirement.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /api/auth/refresh | Refresh cookie attacker-controllable; rotated on each use |
| browser → /api/auth/logout | Requires valid access token to authenticate the logout |
| FastAPI → Redis | Atomic rotation via pipeline; no race window where both tokens are valid |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03-01 | Elevation of Privilege | Stolen refresh token reuse | mitigate | Rotation: every /refresh deletes the old token in Redis and stores a new one; replay of T1 after T2 issued returns 401 (Pitfall 6) — covered by replay test |
| T-02-03-02 | Tampering | Type-confusion (access token submitted to /refresh) | mitigate | Decode asserts payload["type"] == "refresh"; access tokens lack this claim → 401 |
| T-02-03-03 | Information Disclosure | Logout does not revoke server-side | mitigate | revoke_refresh_token deletes Redis key; subsequent /refresh attempts return 401 — covered by logout test |
| T-02-03-04 | Denial of Service | Infinite refresh-retry loop in api.ts | mitigate | didRetry flag in apiFetch; second 401 throws terminal error and clears store |
| T-02-03-05 | Spoofing | Refresh endpoint abuse for token enumeration | mitigate | @limiter.limit("20/minute") on /refresh; consistent 401 detail string regardless of failure cause |
| T-02-03-06 | Repudiation | No audit log of logout / refresh | accept | MVP scope; structured logging deferred to ops phase |
</threat_model>
